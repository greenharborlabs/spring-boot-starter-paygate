## Goal
Implement only [Phase 0 T6](../plans/wavelength-phase-0.md#implementation-tasks): a minimal pinned browser harness persists and validates the original L402 challenge before one Wavelength dispatch, verifies a recovered preimage, retries/reconstructs only that challenge, and reconciles delayed/lost-response/reload outcomes without redispatch. Acceptance is deterministic recovery coverage plus clean-profile execution from the shipped local server and documented headers; payer preimage availability remains an unpassed T7 live gate.

Approval of this record explicitly authorizes a separately reviewed, narrow local parser/formatter limited to Paygate's bounded L402 challenge grammar and `L402 <macaroon>:<64-hex-preimage>` output; no generic codec, automatic payer, wallet adapter, or repayment fallback is authorized. ## Decisions
- Build framework-free TypeScript with an injected public `WavelengthClient` boundary. The production entry creates only the pinned browser client/runtime; lifecycle operations are exposed as operator actions and are not called by the payment state machine. Deterministic tests use a public-shape fake and real Web Crypto/storage semantics.
- Use same-origin `sessionStorage` for one schema-versioned, bounded recovery record: invoice, macaroon, exact GET target, payment hash, verified expiry, creation time, and conservative `dispatchMayHaveOccurred=true` written before dispatch. Do not persist `sendIntentId`; v0.1.1 documents it as short-lived/single-use, while payment-hash activity replay is the supported recovery candidate. Validate every stored field before use and fail blocked on corruption or storage loss.
- Sequence `prepareSend`, subscribe/start replay, durable record write, then exactly one `sendPrepared`. Match only send activity carrying the stored hash; require terminal `complete` plus a 32-byte preimage whose Web Crypto SHA-256 equals the invoice hash. Retain metadata through protected 200; clear only on 200, supported conclusive no-payment/cancellation evidence, or explicit warned abandonment.
- Pin a minimal Node/TypeScript/bundler/test/browser toolchain in the browser lockfile. Serve bundled code and the eight externally supplied hash-verified runtime files from loopback with explicit CSP, content types, cache policy, and any observed worker/OPFS/COOP/COEP requirements. Use a temporary clean Playwright Chromium profile with tracing, HAR, video, and screenshots disabled; document exactly what synthetic startup proves and leave real wallet/preimage behavior to T7.

### Attempt 1
Reviewed revision: bfbacd71a2fcb21a8890356523e68160ea1c712c
Verdict: rework
Findings and dispositions:
1. **P1 — Concurrent `dispatch()` calls can each reach `sendPrepared`, defeating the one-dispatch guarantee.** In `paygate-integration-tests/src/wavelengthSpike/browser/src/payment-harness.ts`, `BrowserPaymentHarness.dispatch` uses only `this.store.load() !== null` as its re-entry guard. That check runs before the first suspension point (`await this.client.prepareSend(...)`) and before the durable `this.store.save(...)`, so two overlapping calls both observe an empty store, each run `prepareSend`/`ActivityMonitor.start`, then both `save` (the second overwrites the first), and both invoke `sendPrepared`. This contradicts the record's own Goal/Constraints ("exactly one `sendPrepared`", "an unresolved record blocks every new payment action") and is a double-payment risk: each call prepares its own `sendIntentId`, so the daemon single-use guard on a shared intent does not apply. Reproduced deterministically: two concurrent `dispatch(CHALLENGE, TARGET)` calls against a `FakeClient` with delayed `prepareSend`/`startActivity` produced `dispatchCount === 2` with both calls resolving `{state:"unlocked",detail:"none"}`. Rework: make `dispatch` re-entry-safe with a synchronously-set in-flight guard (or an equivalent serialized/lock mechanism such as `navigator.locks`) that rejects the overlapping call without preparing or dispatching, while keeping the durable record as the cross-reload guard; add a deterministic test asserting `sendPrepared` is invoked exactly once under overlapping `dispatch` calls.
2. No other correctness, security, or acceptance findings. The scoped diff is limited to the recorded paths; the tree is clean at the reviewed revision. The parser/formatter boundary is strict (exact `version="0"` grammar, identical canonical `token`/`macaroon`, bounded ASCII, canonical base64, `L402 <macaroon>:<64-hex-preimage>`, same-origin fragment-free `GET` target), persists no preimage or Authorization value, re-validates every stored field before use, fails closed on storage read/write/cleanup or corruption, matches only send activity by stored payment hash, verifies `sha256(progress.preimage)` against the invoice hash, never redispatches during `recover`, and clears only on protected 200 or explicit warned abandonment. The 503 retry is bounded to the documented five retries plus the initial attempt, and failed/timeout activity stays blocked because it cannot prove non-payment. Documentation claims match implementation and observed evidence; remaining live preimage/reload claims stay marked as unpassed T7 gates.
3. Non-blocking note (no rework required): `protocol.ts` accepts only `decoded.network === "tb"` while the JVM decoder and docs say "signet-family" (`lntb`/`lntbs`). The pinned Wavelength v0.1.1 `lightning-kmp-core-jvm:1.13.0` jar only emits `lnbc`/`lntb`/`lnbcrt` (verified via `javap` on the vendored jar), so this is fail-closed rather than incorrect, and T7's real-invoice cross-check remains the recorded live gate.
